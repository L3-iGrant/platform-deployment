# Tests

The tests of the chart. They run without a cluster.

[Back to the contents](../README.md#contents)

`tests/render-matrix.sh` checks the chart without a cluster:

- no em dash or en dash in any text file of the repository (also `docker-compose/`, `scripts/`, `images/` and `.github/`; not the licence texts of other projects); the text of the chart files and of the docs (British English, no names of other key store products), and the relative links of `README.md` and `docs/` (`tests/check_links.py`: each target file and each anchor heading exists). Each image of `values.yaml` is in [Images](images.md), each image of another project is in `THIRD-PARTY-NOTICES.md`, and the licence texts of Valkey and redis_exporter are in `licenses/`;
- every combination of the profiles, without consent (the default), also with `tests/check_installation.py` (2 database choices, 2 OpenBao choices, 6 exposure profiles, with and without network policies; a default has no profile). Each render goes through `helm template`, `kubeconform -strict` (if installed), `tests/check_hook_order.py install` (see below) and `tests/check_render.py`, which checks:
  - the engine, host, port and TLS of each configuration file, and the server and Jobs of the engine;
  - the exposure objects (on premise: only the wallet host on the public IngressClass; never a route to the wallet's config role);
  - the OpenBao seal, and the database port in the network policies;
  - the parameters of the bundled server (each name once, and the DDL and connection logs), and the init script (psql `\password`, no password in a statement);
  - the kinds and weights of the database hooks (the Secrets, the init hook, the roles hook, the migration hooks and the read access hooks), and the migration of the api and consent when their pods start;
  - the wallet's database roles: the user and Secret key of each wallet process, and no password of the database owner user in a wallet pod or Job;
  - the audit log retention and the retention purge in each wallet file and in the migration hook, and no audit bucket by default;
  - the bundled Valkey: its objects (none is a hook), the settings of the data servers and Sentinels, the ACL users and their rights, no password in the ConfigMap, the `redis` section and Valkey files of each wallet role, and the Valkey files of the gateway.

  One more render checks the bundled server with the DDL and connection logs off;
- the network policies of each render with `network-policies.yaml`: `tests/check_network_matrix.py` applies the policies to the pods of the release as Kubernetes does. It proves that each connection of `policies/network-matrix.yaml` is allowed, that every other connection between the pods of the release is denied, and that each forbidden pair is denied. With the pods of the ingress controller of the exposure profile (`tests/fixtures/ingress-controller-pods.yaml`: Envoy Gateway, also for the chart defaults; ingress-nginx; not kgateway), it also proves the connections with these pods: they reach only the gateway, the wallet service and the dashboard, and only the roles of `externalConnections` reach them, only on the ports of their listeners (Envoy Gateway: 10080 and 10443). The Envoy Gateway controller and the Envoy pods of another Gateway get no connection;
- the files of `manifests/envoy-gateway/` (the Gateway of the default exposure): `kubeconform -strict` (if installed) with the Gateway API, Envoy Gateway and cert-manager schemas of the CRDs catalog;
- your own Valkey or Redis (`redis-external.yaml`, with two database choices, with and without network policies): no Valkey object, the `redis` section of each wallet role, the Secrets of the users, and egress to your servers only from the wallet roles and the gateway;
- consent (`consent.yaml`): each exposure profile, with and without network policies, with the same checks and `tests/check_installation.py`; the tests after the matrix use `consent.yaml`, and `exposure-envoy-gateway.yaml` where they pick an exposure;
- the minimal profile (`minimal.yaml`, with and without network policies): one replica of each service except the worker groups, and 3 Valkey pods;
- the image pull Secrets of `global.imagePullSecrets` in every pod spec: the Deployments, StatefulSets, Jobs and hooks, also the optional ones;
- the certificate of the bundled Valkey: the names of the pods, of the Sentinel Service, and 127.0.0.1;
- the Valkey metrics: the exporter in each pod (the user `metrics`, no CONFIG, only the CA), its ACL user and password, the ServiceMonitor, the scrape port with network policies, none of them by default, and their guards;
- the wallet's separate groups (`redis.state`, `redis.cache`): the endpoints `state` and `cache` in each wallet file, the CA of a group in the wallet pods and not in the gateway, egress to `networkPolicy.externalRedis` only from the wallet roles, and the guards;
- the render guards (wrong values stop the render with a clear message, for example `database.engine: mysql`);
- the api's operator Jobs (`tests/check_operator_jobs.py`, with `tests/values/operator-jobs-bootstrap.yaml`): no operator Job with the default values; the platform operator of a new installation (`bootstrapPlatform`: the arguments of `onboard bootstrap-platform` after `migrate`); the password only as a file of its own Secret, never an argument, a variable or a ConfigMap value; the guards of the required values and of a password as a value;
- the webhook event types: no `Webhooks.events` in the api files, and the schema refuses `api.webhooks.events`;
- the gateway feature gate (`gateway.features.enforce`): `Features.enforce` `true` in the gateway file of each render and in no api file, `false` with the value, and the schema guard;
- the services of the installation (`tests/check_installation.py`; see [Components](components.md#the-services-of-the-installation)). With all services, and with consent or the wallet of another release: no `Installation` key. Without consent and without the wallet (also with network policies and an external database, and without the keys and NATS users of the missing service): `Installation.services` in the api, webhook and gateway files only; no upstream, object, read-only user, trusted issuer, service keys file, NATS user or Valkey user of the missing service; without the wallet, no key `ReadAccess.wallet` in the consent file, no read access Job of consent for the wallet, no rights on the consumers `consent-dda-present-proof` and `consent-dda-presentation` for the NATS user of consent, and no `OpenIdDeployment` and no `walletUrl`. Also the install and network matrix of each case; the upgrades that install or remove consent or the wallet; the connection budget and the notes without a service; and the guards (no service, the privacy dashboard without consent, `api.extraConfig.Installation` or `gateway.extraConfig.Installation` with other services);
- the installation limits (`api.limits.maxOrganisations`, `organisationWallet.walletUnit.organisationWalletUnitsMax`): no key in each render of the matrix and with empty values. With a value: `Limits.maxOrganisations` in the api and webhook files and `wallet_unit.organisation_wallet_units_max` in the service, config and worker files, as integers (also from a JSON number), and in no other object (not the gateway file, the clock, the hooks or the Jobs). The schema guards (0, above the maximum, a string);
- the api events: the NATS user `api` publishes each subject of `API_EVENTS` by name, with `api.v1.evt.organisation.deleted`, and the wallet commands `ows.cmd.>`;
- install and upgrade: `tests/check_hook_order.py` replays the Helm steps on the renders, without a cluster: the hooks in the order of their weights, the resources of the release, and on an upgrade the objects of the earlier release and the deletion of the resources that the new release does not have (except the objects with `helm.sh/resource-policy: keep`). When each hook Job starts, the Secrets, ConfigMaps, databases and users that it needs must exist. The cases: each render of the matrix as an install; on both database files, installs with consent, the api or the organisation wallet off (no read access Job of a reader that is off), an upgrade with the same values, and upgrades that turn the organisation wallet, consent or the api on. A copy of the chart reads earlier Secrets from a file instead of `lookup`: the Secrets that are hooks keep the values of the earlier Secrets, and the Secrets of the bundled Valkey and the TLS Secret of the bundled NATS (normal resources, not hooks) keep their passwords and certificates;
- the wallet's workers and clock (in each render of the matrix): the Deployment of each worker group (its command with the queues, the health port and the probes, the stop budget, the state folder, its configuration key); the clock (2 replicas, its command, its file with only the database, the NATS address, `kms`, Valkey and its health port, and only the database and Valkey files); the database role, NATS user and Valkey user of each; the guards of the worker groups (a name, a duplicate name, a long Deployment name, a queue, a duplicate queue, a queue that no group runs, the stop budget, the replicas); the ServiceMonitor; and the scrape of the health ports with network policies;
- the replicas (in each render): the replicas, CPU requests and memory limits of the api, the webhook handler and the wallet service, config, clock and workers, and no disruption budget, default anti-affinity, zone spread or HorizontalPodAutoscaler (they belong to the scaled deployment);
- the bundled NATS (in each render): the TLS of the clients and the mutual TLS of the routes with the chart's TLS Secret (kept, not a hook), and the NATS CA in each process with a NATS user; the names of its certificate (`openssl x509`), `nats-server -t` of its configuration (if `nats-server` is installed), your own certificate, an external NATS with and without its CA, and the guard of `nats.tlsCa` with the bundled NATS; the rights of the wallet's webhook events (each wallet role publishes them, the webhook handler has their durable consumer, and the API core and the webhook handler can only read and delete the retired durable consumers of the api); the one wallet command of the webhook handler (`ows.cmd.*.issuance.revoke`); the clears of the process caches (only the service and config users of the wallet publish and subscribe to `ows.cache.cleared`);
- the write interval of the issuer status lists (`organisationWallet.statusList.writeIntervalSeconds`): the value only in the worker files, and the schema guard;
- the nonce limit of the server roles (`organisationWallet.server.nonceRequestsPerMinute`): the value in the wallet files, and the schema guards;
- the server metrics: `server.metrics_port` 9190 and `server.metrics_directory` on an emptyDir in each server file and pod, the probes on the port of the routes, no port 9190 in the Services of the routes, the metrics Services and the job label of the ServiceMonitor, and the scrape open only to the monitoring namespace;
- the connection budget: the render stops when the pools of the release (with the most pods of the autoscalers) and the hooks need more than `max_connections` of the bundled server minus its reserved connections (at the limit and one over it, the reserved connections, more replicas); no check with an external server; and the sum in the notes;
- the connection pools (in each render): the session and allocation pools of the wallet service and config roles, one session connection for each thread of a worker process, no pool value in the clock file, the reader pool of the api and of the webhook handler, and the guards of the pool values;
- the wallet's audit log: the bucket only in the configuration and pods of the worker groups, with its service account or the Google default credentials, the retention in each wallet file and the migration hook, and the guards of the audit values;
- the writable paths of the pods with a read-only root file system: the `emptyDir` of `/tmp` of the api, webhook, dashboard and wallet pods (the api `/tmp` in memory with `api.tmp.sizeLimit`; the worker `/tmp` in memory, 64Mi), the socket folder of the bundled PostgreSQL and the pid folder of NATS; the guards of the api `/tmp` (below the largest gateway body above 32 MiB, or with the memory request above the memory limit); and a render for uploads of 100 MiB;
- the limits of the api's CSV import (`api.extraConfig.Uploads`) in the dashboard's `config.json`: none by default and none for 0, the set values as whole numbers, the stop for a value that the api refuses (also a text of digits such as `"5000"`, which the api cannot read), and a new checksum of the dashboard pods;
- no log file: the render stops with `Log.file.path` in `api.extraConfig`, `gateway.extraConfig` or `consent.extraConfig`, and with `log_file.path` in `organisationWallet.extraConfig`, also below `/tmp`;
- the JetStream store of the bundled NATS: the user and the group 65532, `fsGroup` and `fsGroupChangePolicy: OnRootMismatch`, and no init container;
- `global.podSecurityContext` and `global.containerSecurityContext`: each pod and container gets the keys that its component does not set (SELinux options, supplemental groups), the keys of the component stay, and the notes name each component whose own value sets a global key (the list from `values.yaml`);
- the security settings of the containers (see [Security settings of the containers](security-context.md)): each container of each render of the test, and one render with the optional containers (the Valkey exporter, the api's operator Jobs, the `/tmp` volume claims of the workers). `tests/check_security.py` checks: a non-root user with a UID and a GID other than 0, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, all capabilities dropped and none added, not privileged, seccomp `RuntimeDefault`, no host port, and the SELinux, AppArmor (field and annotation), `procMount` and `hostProcess` rules of the Pod Security Standard, also for the ephemeral containers; and that each pod has no host namespace, only the volume types of the Pod Security Standard `restricted`, and only safe sysctls. `tests/psscheck` (Go, the upstream library `k8s.io/pod-security-admission`, the code of the Kubernetes admission plugin) checks the level `restricted` (latest and v1.25) on the same renders; it must read the same count of containers as `check_security.py`, and it stops at a document that it cannot read or at an unknown kind with containers. Both checks must refuse the mutant `tests/values/pss-mutant.yaml` (AppArmor `Unconfined`, SELinux `spc_t`, `procMount: Unmasked`, `hostProcess`) and each bad pod of `tests/fixtures/pss-pods.yaml` (also an ephemeral container and an AppArmor annotation), and pass its good pod.

```bash
tests/render-matrix.sh            # or: tests/render-matrix.sh --keep /tmp/renders
```

`tests/render-matrix.sh` needs `helm` (it passes with Helm 3.22.1 and 4.3.2), `python3` with PyYAML, `openssl` and Go (the version in `tests/psscheck/go.mod`, for the upstream security check). It uses `kubeconform` and `nats-server` if they are installed.

`tests/compose-files.sh` checks the files of `docker-compose/` without a container:

- `docker compose config` for the engine;
- the configuration files of the components, the DDL and connection logs of the database server, and the passwords of `database-init` (psql `\password`);
- the scripts and the NATS configuration;
- the Valkey services with their templates and ACL users, and the `redis` section of each wallet file;
- the gateway feature gate (`FEATURES_ENFORCE`);
- the installation limits (`MAX_ORGANISATIONS`, `MAX_ORGANISATION_WALLET_UNITS`: the keys are in the api, webhook and wallet files only with a value);
- the webhooks of the api files (no `Webhooks.events`), and no `Installation` key (Compose installs all services);
- the platform operator targets of the Makefile (`make -n`: the api commands, and the password on standard input);
- the configuration files (`make configs`, `render-configs.py`): the templates of `compose.configs.yaml` and one config of `file` of `generated/` for each, no config of `content`, the same values files for the render and the services, the hash label of each service and its file, only the variables of `.env.example` in the templates (so no secret), no secret value in a file, and the renderer in a copy of the folder (`$$`, `${VAR:+...}`, a missing value, the file modes, a stale file, `--check`, a second run);
- the security settings of each service of all profiles (a service that the test does not know fails): a read-only root file system, a non-root user, no capability, no new privileges, the tmpfs and volumes of the writable paths, no host namespace, no device, only bind mounts of `secrets/`, the sysctl of the ports below 1024, no shell in the api image, and the one-shot services that run as root, such as `nats-data-owner`, with only their capabilities and no network;
- the same text rules, and the relative links of its README.

These tests run containers of local images. They never pull, the containers have unique names, and the scripts remove them at the end. They take the images as arguments, for example the images of `redis.image` and `nats.image`:

```bash
tests/valkey-pods.sh valkey/valkey:8.1.11-alpine     # the pods of the bundled Valkey
tests/compose-valkey.sh valkey/valkey:8.1.11-alpine  # the Valkey services of docker-compose/
tests/nats-routes.sh nats:2.14.10-alpine            # only the NATS servers of the chart open a route
tests/alert-rules.sh prom/prometheus:v3.13.5         # the alert rules of the wallet (promtool)
tests/tls-strict.sh python:3.13-slim-trixie          # the TLS certificates against the strict checks of Python 3.13
tests/wallet-commands.sh <registry>/eudi-wallet:<tag> # each wallet command of the chart and of Compose in the wallet image
```

- `tests/valkey-pods.sh` renders the chart and runs three containers as the three pods of `<release>-redis`, with the files of the render (the ConfigMap, the TLS Secret, the users Secret) and the pod DNS names. It tests the first start (one primary, the replicas in sync, the Sentinels log in to each other, the settings), the ACL rights of each user (also `metrics`: `INFO`, the slow log length and the latency, and no key, no CONFIG, no slow log entry, no client list), a planned stop of the primary (`prestop.sh`), an unplanned stop, a restart of all Sentinels, and a restart of all pods with the data kept.
- `tests/compose-valkey.sh` reads the services `valkey`, `valkey-replica` and `valkey-sentinel` from `docker compose config` and runs them with test passwords. It tests the start in the order of `depends_on` with their healthchecks, the ACL rights, the `redis` section of each wallet role, a failover, and a restart of the old primary as a replica.

- `tests/nats-routes.sh` renders the chart with 3 NATS servers and runs them as the 3 pods (the configuration and TLS Secret of the render, the names of the headless Service): they form the cluster with mutual TLS. Then three intruders try to open a route: a server with a certificate of its own CA, a server without the TLS block for its routes, and a raw route `CONNECT` without TLS. Each server refuses each intruder, each server keeps only its 2 peers, and all servers keep running.
- `tests/alert-rules.sh` renders the wallet's PrometheusRule (`organisationWallet.prometheusRule`), checks its rules with `promtool check rules`, and runs the unit tests of `tests/fixtures/alert-rules-test.yaml` with `promtool test rules`: a stopped audit export is critical after 10 minutes (one alert for two worker pods), partitions that wait for their export index are a warning after 8 hours (a wait that ends sooner gives no alert), a missing partition for the month is critical, and a late revocation is a warning; another namespace, and a scope with 0, give no alert.

- `tests/tls-strict.sh` takes the TLS Secrets that the chart makes (PostgreSQL, OpenBao, NATS, Valkey), and checks each with `openssl verify -x509_strict` and with a TLS connection in Python 3.13 (`ssl.create_default_context`, strict by default); a control without key identifiers must fail both.
- `tests/wallet-commands.sh` runs each wallet container and Job of the chart, and each wallet service of `docker-compose/`, in the wallet image (no shell, no entrypoint script), as the pods run them: each must be a full command of `/app/.venv/bin`, and the program must start. It needs the wallet image of the release (not public): run it before a release.

`tests/render-matrix.sh` also runs `tests/check_lifecycle.py` on each render: no exec probe or hook in an image without a shell, no exec of `/bin/sleep`, no `initialDelaySeconds` with a startup probe, and for each HTTP Deployment the rollout (`maxUnavailable: 0`, `maxSurge: 25%`, `minReadySeconds`), the preStop sleep, and a grace period that covers the sleep and the stop of the server. The check must refuse each bad pod of `tests/fixtures/lifecycle-pods.yaml`.

The workflow `.github/workflows/tests.yaml` runs `tests/render-matrix.sh` (once with Helm 3.22.1 and once with Helm 4.3.2), `tests/compose-files.sh`, `tests/tls-strict.sh` and the three Valkey and NATS tests on each pull request and each push to `main` (`tests/ci-tools.sh` installs `helm` (`HELM_VERSION`, default 4.3.2), `kubeconform` and `nats-server` with checked SHA-256 sums, and PyYAML).
