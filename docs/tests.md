# Tests

This page describes the tests of the chart. They run without a cluster.

[Back to the contents](../README.md#contents)

`tests/render-matrix.sh` checks the chart without a cluster:

- the text of the chart files and of the documentation (no em dash, British English, no name of other key store products), and the relative links of `README.md` and `docs/` (`tests/check_links.py`: each target file and each heading of an anchor exists); each image of `values.yaml` is in [Images](images.md), each image of another project is in `THIRD-PARTY-NOTICES.md`, and the licence texts of Valkey and of redis_exporter are in `licenses/`;
- every combination of the examples (2 database files, 2 OpenBao files, 6 exposure files, with and without network policies): `helm template`, `kubeconform -strict` when it is installed, and `tests/check_render.py` (the engine, host, port and TLS of each configuration file, the server and the Jobs of the engine, the exposure objects (on premise: only the wallet host on the public IngressClass; never a route to the config role of the wallet), the OpenBao seal, the database port of the network policies, the parameters of the bundled server (each name once, and the DDL and connection logs), the init script (psql `\password`, no password in a statement), the kinds and weights of the hooks of the databases (the Secrets, the init hook, the roles hook, the migration hooks and the read access hooks), the migration of the api and consent when their pods start, and the database roles of the wallet: the user and the Secret key of each wallet process, and no password of the database owner user in a wallet pod or Job; the retention of the audit log and the retention purge in each wallet file and the migration hook, and no audit bucket by default; the bundled Valkey: its objects and that none is a hook, the settings of the data servers and of the Sentinels, the ACL users and their rights, no password in the ConfigMap, the `redis` section and the Valkey files of each wallet role, the Valkey files of the gateway), and `tests/check_hook_order.py install` (see below), and one more render of the bundled server with the DDL and connection logs off;
- the network policies of each render with `networkpolicy.yaml`: `tests/check_network_matrix.py` applies the policies to the pods of the release as Kubernetes does, and proves that each connection of `policies/network-matrix.yaml` is allowed, that each other connection between the pods of the release is denied, and that each forbidden pair is denied;
- your own Valkey or Redis (`redis-external.yaml`, with two database files, with and without network policies): no Valkey object, the `redis` section of each wallet role, the Secrets of the users, and the egress to your servers only from the wallet roles and the gateway;
- the certificate of the bundled Valkey: the names of the pods, of the Service of the Sentinels and 127.0.0.1;
- the metrics of Valkey: the exporter in each pod (the user `metrics`, no CONFIG, only the CA), its ACL user and password, the ServiceMonitor, the scrape port with network policies, nothing of them by default, and their guards;
- the separate groups of the wallet (`redis.state`, `redis.cache`): the endpoints `state` and `cache` in each wallet file, the CA of a group in the wallet pods and not in the gateway, the egress to `networkPolicy.externalRedis` only from the wallet roles, and the guards;
- the render guards (wrong values stop the render with a clear message, for example `database.engine: mysql`);
- the operator Jobs of the api (`tests/check_operator_jobs.py`, with the files `tests/values/operator-jobs-*.yaml`): no operator Job with the default values; the three Jobs of the earlier releases (`registerAdmin`, `createOrganisationType`, `createOrganisation`) with their values file of the earlier install page; the platform operator of a new installation (`bootstrapPlatform`: the arguments of `onboard bootstrap-platform`) and of an installation that exists (`platformOperator`: `platform set-operator` in an init container after `migrate`, then `platform grant-admin`); the password only as a file of its own Secret, never an argument, a variable or a ConfigMap value; the guards of the required values, of the two paths together and of a password as a value;
- the webhook event types: no `Webhooks.events` in the api files, also with `api.webhooks.events` of an earlier values file (the schema accepts it), and the warning of the notes;
- the feature gate of the gateway (`gateway.features.enforce`): `Features.enforce` `true` in the gateway file of each render and in no api file, `false` with the value, and the schema guard;
- the services of the installation (`tests/check_installation.py`; see [Components](components.md#the-services-of-the-installation)): with all services, and with consent or the wallet of another release, no `Installation` key; without consent and without the wallet (also with network policies and an external database, and without the keys and the NATS users of the missing service), `Installation.services` in the api, webhook and gateway files only, no upstream, object, read-only user, trusted issuer, service keys file, NATS user or Valkey user of the missing service, no key `ReadAccess.wallet` in the consent file and no read access Job of consent for the wallet without the wallet, no rights of the consumers `consent-dda-present-proof` and `consent-dda-presentation` for the NATS user of consent without the wallet, no `OpenIdDeployment` and no `walletUrl` without the wallet; the install and the network matrix of each case; the upgrades that install or remove consent or the wallet; the connection budget and the notes without a service; the guards (no service, the privacy dashboard without consent, `api.extraConfig.Installation` or `gateway.extraConfig.Installation` with other services);
- the limits of the installation (`api.limits.maxOrganisations`, `organisationWallet.walletUnit.organisationWalletUnitsMax`): no key in each render of the matrix and with empty values; with a value, `Limits.maxOrganisations` in the api and webhook files and `wallet_unit.organisation_wallet_units_max` in the service, config and worker files, as integers (also from a JSON number), and in no other object (not the gateway file, the clock, the hooks or the Jobs); the schema guards (0, over the maximum, a string);
- the events of the api: the NATS user `api` publishes each subject of `API_EVENTS` by name, with `api.v1.evt.organisation.deleted`, and the wallet commands `ows.cmd.>`;
- install and upgrade: `tests/check_hook_order.py` replays the steps of Helm on the renders, without a cluster: the hooks in the order of their weights, the resources of the release, and on an upgrade the objects of the earlier release and the delete of the resources that the new release does not have (except the objects with `helm.sh/resource-policy: keep`). When each hook Job starts, the Secrets, ConfigMaps, databases and users that it needs must exist. The cases: each render of the matrix as an install; on both database files, installs with consent, the api or the organisation wallet off (no read access Job of a reader that is off), an upgrade with the same values, upgrades that turn the organisation wallet, consent or the api on, and the first upgrade from a release in which the database Secret, the read access Secret and the init Job were resources. A copy of the chart reads earlier Secrets from a file in place of `lookup`: the Secrets that are hooks keep the values of the earlier Secrets, and the Secrets of the bundled Valkey and the TLS Secret of the bundled NATS (normal resources, no hooks) keep the passwords and the certificates;

- the workers and the clock of the wallet (in each render of the matrix): the Deployment of each worker group (its command with the queues, the health port and the probes, the stop budget, the state folder, its configuration key), the clock (2 replicas, its command, its file with only the database, the NATS address, `kms`, Valkey and its health port, and only the files of the database and of Valkey), the database role, the NATS user and the Valkey user of each; the guards of the worker groups (a name, a name two times, a long Deployment name, a queue, a queue two times, a queue that no group runs, the stop budget, the replicas), the ServiceMonitor, and the scrape of the health ports with network policies;
- the replicas (in each render): the replicas, the CPU requests and the memory limits of the api, the webhook handler and the wallet service, config, clock and workers, and no disruption budget, default anti-affinity, zone spread or HorizontalPodAutoscaler (they belong to the scaled deployment);

- the interval of the writes of the issuer status lists (`organisationWallet.statusList.writeIntervalSeconds`): the value only in the files of the workers, and the schema guard;
- the nonce limit of the server roles (`organisationWallet.server.nonceRequestsPerMinute`): the value in the wallet files and the schema guards;
- the metrics of the servers: `server.metrics_port` 9190 and `server.metrics_directory` on an emptyDir in each server file and pod, the probes on the port of the routes, no port 9190 in the Services of the routes, the metrics Services and the job label of the ServiceMonitor, the scrape open only to the monitoring namespace;
- the connection budget: the render stops when the pools of the release (with the most pods of the autoscalers) and the hooks need more than `max_connections` of the bundled server less its reserved connections (at the limit and one over it, the reserved connections, more replicas), no check with an external server, and the sum in the notes;
- the connection pools (in each render): the session and allocation pools of the wallet service and config roles, one session connection for each thread of a worker process, no pool value in the clock file, the reader pool of the api and of the webhook handler; the guards of the pool values;
- the audit log of the wallet: the bucket only in the configuration and the pods of the worker groups, with its service account or the Google default credentials, the retention in each wallet file and the migration hook, and the guards of the audit values;
- the writable paths of the pods with a read-only root file system: the `emptyDir` of `/tmp` of the api, webhook, dashboard and wallet pods (the api `/tmp` in memory with `api.tmp.sizeLimit`; the worker `/tmp` on disk with `organisationWallet.workers.tmp.sizeLimit`, or a generic ephemeral volume), the socket folder of the bundled PostgreSQL and the pid folder of NATS, and the guards of the worker `/tmp` size; the guards of the api `/tmp` (below the largest body of the gateway above 32 MiB, or with the memory request above the memory limit), and a render for uploads of 100 MiB;
- no log file: the render stops with `Log.file.path` in `api.extraConfig`, `gateway.extraConfig` or `consent.extraConfig`, and with `log_file.path` in `organisationWallet.extraConfig`, also below `/tmp`;
- the JetStream store of the bundled NATS: the user 65532, `fsGroupChangePolicy: OnRootMismatch`, and the init container `store-check` (the script `files/nats/store-check.sh` in the ConfigMap, read-only mounts); and the `fsGroupChangePolicy` of a rollout, with a copy of the chart that reads the NATS StatefulSet in the cluster from a file in place of `lookup`: `Always` when it runs NATS as root (the earlier release, or a rollback to it, also as the container user 0) or when its rollout is not complete, `OnRootMismatch` at an install and after a complete rollout of the non-root release, the value `Always` of your values, and the notes of each case;

Both checks must refuse the mutant `tests/values/pss-mutant.yaml` (AppArmor `Unconfined`, SELinux `spc_t`, `procMount: Unmasked`, `hostProcess`) and each bad pod of `tests/fixtures/pss-pods.yaml` (also an ephemeral container and an AppArmor annotation), and pass its good pod.

```bash
tests/render-matrix.sh            # or: tests/render-matrix.sh --keep /tmp/renders
```

`tests/render-matrix.sh` needs `helm`, `python3` with PyYAML, `openssl` and Go (the version of `tests/psscheck/go.mod`, for the upstream security check), and uses `kubeconform` and `nats-server` when they are installed.

`tests/compose-files.sh` checks the files of `docker-compose/` without a container: `docker compose config` for the engine, the configuration files of the components, the DDL and connection logs of the database server, the passwords of `database-init` (psql `\password`), the scripts, the NATS configuration, the Valkey services with their templates and ACL users and the `redis` section of each wallet file, the feature gate of the gateway (`FEATURES_ENFORCE`), the limits of the installation (`MAX_ORGANISATIONS`, `MAX_ORGANISATION_WALLET_UNITS`: the keys in the api, webhook and wallet files only with a value), the webhooks of the api files (no `Webhooks.events`) and no `Installation` key (Compose installs all services), the platform operator targets of the Makefile (`make -n`: the commands of the api, and the password on standard input), the configuration files (`make configs`, `render-configs.py`: the templates of `compose.configs.yaml` and one config of `file` of `generated/` for each, no config of `content`, the same values files for the render and for the services, the hash label of each service and its file, only the variables of `.env.example` in the templates, so no secret, no secret value in a file, and the renderer in a copy of the folder: `$$`, `${VAR:+...}`, a missing value, the file modes, a stale file, `--check`, a second run), the security settings of each service of all profiles (a service that the test does not know fails: a read-only root file system, a non-root user, no capability, no new privileges, the tmpfs and volumes of the writable paths, no host namespace, no device, only bind mounts of `secrets/`, the sysctl of the ports below 1024, no shell in the api image, and the one-shot services of root, such as `nats-data-owner`, with only their capabilities and no network), the same text rules and the relative links of its README.

Three tests run real servers in containers of local images (they never pull; the containers have unique names, and the scripts remove them at the end). They take the images as arguments, for example the images of `redis.image` and `nats.image`:

```bash
tests/valkey-pods.sh valkey/valkey:8.1.10-alpine     # the pods of the bundled Valkey
tests/compose-valkey.sh valkey/valkey:8.1.10-alpine  # the Valkey services of docker-compose/
tests/nats-store.sh nats:2.12.3-alpine natsio/nats-box:0.18.1 --files 200000   # the JetStream store across a rollback
```

- `tests/valkey-pods.sh` renders the chart and runs three containers as the three pods of `<release>-redis`, with the files of the render (the ConfigMap, the TLS Secret, the users Secret) and the pod DNS names: the first start (one primary, the replicas in sync, the Sentinels log in to each other, the settings), the ACL rights of each user (also `metrics`: `INFO`, the slow log length and the latency, and no key, no CONFIG, no slow log entry, no client list), a planned stop of the primary (`prestop.sh`), an unplanned stop, a new start of all Sentinels, and a new start of all pods with the data kept.
- `tests/compose-valkey.sh` reads the services `valkey`, `valkey-replica` and `valkey-sentinel` from `docker compose config` and runs them with test passwords: the start in the order of `depends_on` with their healthchecks, the ACL rights, the `redis` section of each wallet role, a failover, and a new start of the old primary as a replica.

- `tests/nats-store.sh` plays the NATS pod with a real `nats-server` across an upgrade, a rollback and a roll forward (see [The JetStream store](security-context.md#the-jetstream-store)): NATS of the earlier release as root, the kubelet change of the volume for `fsGroup` (with `Always`, or with `OnRootMismatch` as the kubelet does it), the init container `store-check` with `files/nats/store-check.sh` (as the user 65532, read-only, with its memory limit), and `nats-server` as the user 65532. It shows the failure of the review on a copy of the store (without `store-check`, NATS starts without the stream of the rollback and a publish to it fails), that `store-check` stops the start with `OnRootMismatch` and changes no file, and that `Always` gives back each stream with each message and the consumer. Then it measures the kubelet change, a start with `OnRootMismatch` and `store-check` on a store of `--files` files, and the peak memory of `store-check`.

The workflow `.github/workflows/tests.yaml` runs `tests/render-matrix.sh`, `tests/compose-files.sh` and the three container tests on each pull request and each push to `main` (`tests/ci-tools.sh` installs `helm`, `kubeconform` and `nats-server` with checked SHA-256 sums, and PyYAML). On your computer, run the container tests on a shared Docker host inside your lock of the Docker tests.
